# M1 等价证据归档 —— 同机双进程真互发（不充当出口判据）

**定性（PM 拍板）**：M1 出口原文是「**两台机器**能互发文本并可回看」。
**同机双进程只能算「实现链路真跑通」，不算 M1 出口。** 本文件把这些结果单独归档为**等价证据**，
出口判据另立 `M1-28`（标注「需两台物理机器」），两者不混。

## 二、`verify-im-lan-mutual.ts` 断言覆盖面（对照「发现→验指纹→建链→封包→互发→互收→回看」）

| 环节 | 覆盖 | 说明 |
| --- | --- | --- |
| 发现 | ✅ | 断言 `discovered > 0`（真 mDNS） |
| 验指纹 | ⚠️ **弱** | 调了 `discovery.verify()`，但**没有断言它生效**，且是**自算自核**（拿发现来的公钥自己算指纹再自己核对）；**无「不核对就不建链」的对照** |
| 建链 | ✅ | 断言两侧 `ok === true`（真 wrtc） |
| 封包 | ⚠️ **间接** | `lan-gateway.deliver()` 确实调 `sealImEnvelope`（代码层核实），但**脚本无断言证明走的是封包路径**，只断言 `queued === 1` |
| 互发 | ✅ | A 的帧进了 B 的队列 |
| 互收 | ⚠️ **弱** | 只数 `offline_queue` 行数，**未验内容**（没比对正文/密文） |
| 回看 | ❌ **缺** | 无「读回比对」断言 |

**结论**：7 个环节里 **3 个够、2 个弱、1 个间接、1 个缺**。5/5 是真的，
但它证明的范围比「发现→验指纹→建链→封包→互发→互收→回看」窄——**尤其没有回看与内容比对**。

## 三、必须写明的两条（PM 点名要核的）

1. **loopback 被当成了「真网卡」**：`src/backend/im/mdns-responder.ts:81` 的 `A` 记录**写死 `"127.0.0.1"`**。
   发现到的对端 host 永远解析到回环。所以这套验证的「真实网络」其实是**回环网络**——
   **它不是真机网络下的组播/NAT 穿透**。后端也自报了这一条（差距清单第 1 条）。
2. **设备密钥是预置的**：`im-lan-peer.ts` 用 env（`IM_DEVICE_KEY` / `IM_PEER_DEVICE_KEY`）注入
   `deviceKeyOf`，**不是经设备入网换来的对方 P-256 设备公钥**。封包能跑是因为密钥被调用方塞进去的。
   （后端自报差距清单第 2 条，与我核实一致。）

## 四、与「两台物理机器」还差什么

1. mDNS `A` 记录写死 `127.0.0.1` → 真机要发真实网卡地址
2. 设备密钥交换未接（`deviceKeyOf` 调用方预置）
3. 信令走明文 TCP（`host:port` 直连），跨网段/NAT 连不上，应走中转
4. TURN 兜底只传配置、未实测
5. 真实组播与 NAT 穿透只在本机验过

前 3 条是代码侧，后 2 条要真机。
