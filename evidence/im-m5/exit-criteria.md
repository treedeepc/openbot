## 二、对照组（凡验「A 生效」必带「非 A 的对照仍正常」）

| # | 位置 | 对照断言 | 为什么必须有 |
| --- | --- | --- | --- |
| 1 | D2-3 | **未撤销设备照常取到** | 没有它，一个「把整条消息谁都取不到」的坏修法也能蒙混过关 |
| 2 | D2-3 | 未撤销设备的目标行不被牵连 | 区分「精准排除一台」与「整批标 excluded」 |
| 3 | D2-3 | **未撤销设备的 ACK 照常成功** | 区分「excluded 的 ACK 被拒」与「所有 ACK 都被拒」 |
| 4 | M5-08 | **同一消息的另一台设备照常取到** | 同 1，是本轮点名要带的对照 |
| 5 | M5-11 | 内部状态立即生效（`current()` 当场隐身） | 与「对外 30 秒栅格才暴露」成对，缺一就分不清是延迟还是没生效 |
| 6 | M5-11 | 非好友**始终**被拒（不是只拦第一次） | 区分「鉴权生效」与「第一次碰巧拦住」 |
| 7 | M5-12 | 读回**确实有数据**（不是空结果才没字段） | 没有它，「没返回最后上线时间」可能只是因为什么都没返回 |

| 9 | D2-5 | 另一条不被误标已读 / 已 ack 不可再重发 | 区分状态机回正与全量重置 |

## 五、缺陷 A 结案（本轮唯一的产品缺陷）

| 项 | 内容 |
| --- | --- |
| 现象 | 设备被撤销 / 证书过期后标了 `excluded`，消息仍能被取到，等于照旧重发 |
| 根因 | `exclude()` 只 UPDATE `offline_targets` 不清 `offline_queue`；`pending()` 不反连 targets。铁证：全仓 `offline_targets.state` 只有写入方、零读取方 |
| 位置 | `src/backend/im/server-mode.ts` 的 `exclude()` / `pending()` |
| 修法（后端已按此交付） | ①`exclude` 补 DELETE 清 queue 行 ②`pending` 反连 targets 排除 `state='excluded'` ③`confirm` 加 `#excluded` 守卫 ④`settled` 的「全 ACK 才删」只数**非 excluded** 目标 |
| 影响面 | A8 撤销 + 证书过期两场景；隐私面（吊销设备取不到密文） |
| 复跑 | D2-3（9 断言）、M5-08（5 断言）**双双转过**，对照组 4 处全过 |

## 六、本关卡覆盖不到的（留档，非本关卡验收范围）

- **「关闭已读回执后不发 read / 开启后发 read」验不了**：后端**无已读回执开关**，`markRead` 无条件把该条置 `read`。前端 T11b3 已做「已读回执可关」的界面，但后端没有对应开关，二者不一致。**需后端补开关后复跑 D2-5 前两步**，现交前端 T11b3 证据。
- `setDeliveryState` 是**单调状态机**（不许回退），造不出 `failed` 态；D2-5 的失败前置用 SQL 造（被测点是 resend，不是失败记账）。
- M5-12 的 remote 侧同口径（实例间协议帧）依赖 T7b 跨机链路，本轮只验到 host route + 服务层。
